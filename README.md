# IIVGRPG

Исторический проект браузерной MMORPG с Java-сервером и HTML5/JavaScript-клиентом.
В поздних ревизиях также появился ранний MMORTS-клиент и сервер.
Имя на Google Code — `iivgprg` (с переставленными буквами).

Для игры предназначен [релизный дистрибутив](release/README.md): готовые JAR
и статический клиент. Пользователь создаёт Docker-образы без компиляции,
Maven и Node.js. Спрайты в дистрибутив не входят;
для полноценной графики нужно подключить собственные PNG.

Общая версия клиента и сервера — **2.3.0**.

Ветка `main` содержит полную последовательность 129 ревизий Google Code SVN
за 2011–2012 годы, затем отдельный коммит документации переноса.
`trunk/` развёрнут в корень, `wiki/` сохранён рядом с исходниками.
Сообщения, авторы, даты и байты оставленных файлов сохранены.
Спрайты и дампы БД исключены из **всей истории**, поэтому для запуска понадобятся
собственные совместимые ресурсы и база данных. Код исторический; текущий контейнерный стенд описан ниже.

Для разработки на хосте нужны Docker Engine и Docker Compose. JDK 21, Maven,
Node.js и MariaDB запускаются в контейнерах с UID/GID пользователя хоста. Проекты NetBeans и Eclipse удалены.

## Запуск для разработки

Перед первым запуском, после удаления volumes или смены UID/GID выполнить
настройку от обычного пользователя хоста (без `sudo`):

```sh
sh dev/setup.sh
docker compose up -d
docker compose logs -f
```

Открыть [клиент](http://localhost:5174). В поле Server автоматически подставляется
`ws://localhost:5174/ws/`; прокси Vite передаёт соединение Java-серверу.
Для входа можно использовать `test` / `test`: исторический MMORTS-сервер принимает
любые логин и пароль. Стенд запускает поздний HTML5 MMORTS-клиент и
`mmo.ServerLauncher`. Неиспользуемые ранние клиенты и сервер MMORPG удалены
из текущего дерева. Рабочая сборка MMORPG сохранена в ветке `codex/version-1`
и теге `v1.4.0`. Исходник самостоятельного редактора карт — `client/mapeditor.html`.

Порты опубликованы только на `127.0.0.1`: HTTP — `5174`, прямой WebSocket — `8016`.
Они не пересекаются с портами dev-стенда `minimmorts`.
Изменить их можно через переменные `CLIENT_PORT` и `SERVER_PORT`:

```sh
CLIENT_PORT=5175 SERVER_PORT=8017 docker compose up -d
```

- `client`: Vite раздаёт `client/mmorts/` и перезагружает страницу при сохранении
  HTML/JS. Классические скрипты и их порядок загрузки сохранены. Игровая карта
  переименована из `Map` в `GameMap`, чтобы не перекрывать встроенный класс
  JavaScript, используемый Vite.
- `server`: при старте и изменениях `server/src/`, `server/pom.xml` или
  `dev/server/config.xml` выполняет чистую сборку Maven и запускает JAR.
  Проверка изменений — раз в секунду. При ошибке компиляции предыдущая JVM
  продолжает работать; после исправления сборка повторяется.
- `db`: MariaDB создаёт пустую базу `iivgrpg` и пользователя из dev-конфигурации.
  Java-сервер запускается после готовности БД. Архивный дамп не импортируется:
  текущий MMORTS-режим подключается к БД, но хранит игру в памяти и не обращается
  к таблицам старого MMORPG.

Перезапуск JVM сбрасывает игру и разрывает соединения; для повторного входа
обновить страницу. При аварийном завершении JVM без изменения файлов выполнить
`docker compose restart server`. Команда `up -d` запускает контейнеры, но первая
загрузка зависимостей и компиляция продолжаются в фоне — дождаться в логах
сообщения `Web server bind port 8,015`.

Исходники доступны для редактирования на хосте. У клиента репозиторий смонтирован
для чтения и записи, у сервера — только для чтения. Используется общая метка
SELinux `z`. Кэши Maven/npm, node_modules, результаты сборки, рабочий JAR и данные
MariaDB хранятся в отдельных Docker volumes.

`dev/setup.sh` записывает текущие `LOCAL_UID` и `LOCAL_GID` в локальный `.env`,
сохраняя остальные настройки. Compose использует эти значения и при сборке,
и при запуске всех трёх сервисов. Скрипт создаёт точки монтирования на хосте до
Docker, собирает образы, останавливает сервисы и исправляет владельцев существующих
каталогов и томов. Только эта подготовка выполняет разовые команды от root;
Node.js, Maven, Java, Python и MariaDB работают от пользователя хоста.
Для самостоятельных команд Compose без `.env` используются UID/GID `1000:1000`.

Домашний каталог клиента и сервера — `/home/developer`; npm-кэш находится в
`/home/developer/.npm`, Maven — в `/home/developer/.m2`. Каталог сокета MariaDB
создаётся через tmpfs с теми же UID/GID. Запуск контейнеров не меняет владельца
исходников. Уже существующий `client/cache` от версии 1 также исправляется
скриптом настройки; данные внутри named volumes сохраняются.

## Сборка и проверки

```sh
# Сервер: JAR со всеми зависимостями
# /build/server/target/iivgrpg-server.jar
docker compose exec server mvn -B -ntp clean verify

# Клиент: проверка синтаксиса JS и копирование файлов в /workspace/client/dist/
docker compose exec client npm run build

# HTTP, WebSocket через Vite, вход двух игроков и подтверждение игровых шагов
docker compose exec -T client node /workspace/dev/smoke.mjs

# Терминалы
docker compose exec server bash
docker compose exec client sh

# Остановка с сохранением данных и кэшей
docker compose down
```

Не запускайте ручную Maven-сборку одновременно с автоматической: дождитесь её
завершения в логах. Ручная сборка не заменяет работающую JVM. Для её перезапуска
используйте `docker compose restart server`. Рабочий JAR хранится отдельно от
каталога сборки, поэтому `clean` не затрагивает запущенную игру.

```sh
docker compose cp server:/build/server/target/iivgrpg-server.jar /tmp/iivgrpg-server.jar
docker compose cp client:/workspace/client/dist /tmp/iivgrpg-client
```

JAR запускается командой `java -jar iivgrpg-server.jar /absolute/path/config.xml`.
Без аргумента сервер, как прежде, читает `config-home.xml` из текущего каталога.
Dev-конфигурация — `dev/server/config.xml`, реквизиты БД согласованы с Compose.
Конфигурация релизного стенда — `server/config.xml` (хост БД — сервис `db`).
Статическому клиенту после сборки нужен WebSocket-прокси `/ws/` к серверу
(переписывающий путь в `/`), либо адрес сервера можно вручную указать в форме.

Версии Java-зависимостей сохранены из локальных библиотек: Netty 3.4.4.Final,
Gson 1.7.1 и MySQL Connector/J 5.1.17. Maven загружает их из Central;
локальные копии из `server/libs/` удалены как неиспользуемые.
Исторические файлы доступны в предыдущих коммитах.
Версии инструментов заданы в `dev/*/Dockerfile`, плагины Maven — в
`server/pom.xml`, зависимости клиента — в `client/package-lock.json`.
Это локальный dev-стенд с историческими библиотеками и открытыми dev-паролями.

После изменения Dockerfile повторить `sh dev/setup.sh`, затем `docker compose up -d`.
После изменения package.json обновить lock-файл, затем перезапустить клиент:

```sh
docker compose run --rm --no-deps --user "$(id -u):$(id -g)" -e npm_config_cache=/tmp/npm-cache client npm install --package-lock-only --ignore-scripts --no-audit --no-fund
docker compose restart client
```

Команда обновления lock-файла рассчитана на Linux/macOS.
`docker compose down -v` удаляет все volumes стенда, включая базу данных.
Перед следующим запуском снова выполнить `sh dev/setup.sh`.

## Подготовка релиза

Сборщику нужны Docker с Compose, Python 3.11+ и интернет для получения базовых
образов и зависимостей. На машине игрока нужны только Docker с Compose.

```sh
python3 release/build.py
```

Команда проверяет согласованность версий в package.json, lock-файле, Maven и
релизном Compose, собирает и проверяет клиент и сервер в многоэтапном Dockerfile,
а затем упаковывает готовые файлы, конфигурацию, Dockerfile и Compose в
`release/dist/iivgrpg-2.3.0.tar.gz`. Docker-образы в архив не входят.
Пользователь выполняет `docker compose up -d --build`: Docker скачивает JRE/Nginx/MariaDB
и копирует готовые файлы проекта в локальные образы без инструментов разработки
и компиляции. Повторная упаковка существующего
архива запрещена; для пересборки сначала перенести или удалить старый архив.
Каталоги локальных спрайтов исключены из Docker build context; релизная сборка
также проверяет отсутствие PNG в `dist/`. Исходники и локальные архивные материалы
в дистрибутив не копируются.

JAR и статические файлы не привязаны к архитектуре процессора; архив общий
для amd64 и arm64. Базовые образы при установке выбирает Docker. Запуск на каждой
заявленной архитектуре нужно проверить перед публикацией.

Распаковать результат в отдельный каталог и выполнить команды из его README.
Для сквозной проверки запущенного релиза из корня репозитория:

```sh
docker run --rm --network iivgrpg-release_default \
  -v "$PWD/release/smoke.mjs:/smoke.mjs:ro,z" \
  node:24.11.0-bookworm-slim node /smoke.mjs
```

Проверка использует отдельный контейнер Node: запрашивает страницу и скрипты,
проверяет отсутствие спрайтов и вход двух клиентов через Nginx. Она не проверяет
визуальное отображение игры с пользовательским набором ресурсов.

Перед выпуском обновить общую версию в `client/package.json`, двух полях
`client/package-lock.json`, `server/pom.xml`, `release/compose.yaml` и документации;
завершить запись changelog. После проверки дистрибутива поставить тег `v2.3.0`
на проверенный коммит и приложить архив бинарников к GitHub Release. Сам по себе
автоматический архив исходников GitHub не содержит готовых файлов проекта.

## Ресурсы и история

Для графики нужны локальные `grass.png`, `peasant.png` и `peasant_selected.png`
в `client/mmorts/sprites/`. Они игнорируются Git и автоматически раздаются
dev-сервером. Сборка клиента и релизный архив спрайты не включают: в релизе их
помещают в `sprites/` рядом с `compose.yaml`. Без них сервер и вход работают,
но клиент не сможет полноценно отрисовать игру. Локальные архивы и дампы не входят
в Docker build context. Старые инструкции и клиенты доступны в истории Git.

Дополнения локальных архивов хранятся в пяти независимых ветках `historical/*`.
Они содержат только дополнительные версии файлов, отсутствующие во всех ревизиях
SVN, и описание происхождения. Это неполные деревья; отсутствие файла в такой
ветке не означает его удаление из проекта.

Подробности: [отчёт о переносе](migration/README.md),
[соответствие SVN → Git и учёт локальных копий](migration/import-report.json).
